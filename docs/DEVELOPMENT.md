# Karabas Flasher: информация для разработчиков

Сборка из исходников, установка зависимостей, пакеты, релизы и устройство проекта. Описание для пользователей - в [README.md](../README.md).

Одна кодовая база на Qt6 для Linux, Windows и macOS. Общий код (интерфейс, сеть, логика прошивки)
одинаков везде; всё, что зависит от ОС при работе с дисками, вынесено в `src/Platform.h`
и реализовано отдельно для каждой системы:

| ОС      | Файл                      | Статус |
|---------|---------------------------|--------|
| Linux   | `src/platform_linux.cpp`  | проверен на железе |
| Windows | `src/platform_windows.cpp`| проверен на железе |
| macOS   | `src/platform_macos.cpp`  | проверен на железе |

## Установка на Ubuntu / Debian (.deb)

Готовый пакет лежит в разделе Releases на GitHub (для Ubuntu 24.04 и новее). `apt` сам доставит все
зависимости (Qt 6, udisks2 и т.д.) и установит правило доступа к порту:

    sudo apt install ./karabas-flasher_1.3.2_amd64_ubuntu24.04.deb

**Ubuntu 22.04 и старше:** в их репозиториях нет Qt SerialPort (`libqt6serialport6`), поэтому `.deb` не подойдёт - 
используйте AppImage (Qt внутри). На Debian 12 `.deb` не проверялся: он собран на Ubuntu 24.04 и может требовать более новую glibc.
Запуск: пункт «Karabas Flasher» в меню приложений или команда `KarabasFlasher`.
Для остальных дистрибутивов - сборка из исходников (ниже).

## Другие дистрибутивы

**AppImage (любой дистрибутив).** В релизе есть один файл `KarabasFlasher-<версия>-x86_64.AppImage` с Qt внутри:

    chmod +x KarabasFlasher-1.3.2-x86_64.AppImage
    ./KarabasFlasher-1.3.2-x86_64.AppImage

На некоторых системах нужен пакет `libfuse2` (иначе: `./KarabasFlasher-...AppImage --appimage-extract-and-run`).
Системные части (udisks2, polkit, systemd) должны быть установлены - на обычном рабочем столе они уже есть.
Правило доступа к порту AppImage в систему поставить не может: при ошибке «Доступ запрещён» программа сама
предложит установить его через окно с паролем. Нативного Wayland в образе нет, окно работает через XWayland.

**Arch / Manjaro (PKGBUILD).** Пакет собирается у вас из исходников, зависимости ставятся автоматически:

    cd packaging/arch/git && makepkg -si          # последняя версия из git
    cd packaging/arch/release && updpkgsums && makepkg -si    # версия по тегу vX.Y.Z

Пакет ставит правило udev, пункт меню и иконку. Для сборки из git репозиторий на GitHub должен быть публичным.
Файлы подходят и для публикации в AUR (нужна учётная запись на aur.archlinux.org).

## Сборка

Нужны CMake, компилятор C++17 и Qt 6 с модулями Base и SerialPort.

Распаковка `extra.zip` выполняется библиотекой `minizip-ng`, которая собирается
автоматически через `FetchContent` (исходники скачиваются с GitHub при первой
конфигурации и кэшируются в `build/_deps/`). Внешние архиваторы (`7za`, `7z`,
`libarchive`) не нужны. Для сборки требуется сеть при первой конфигурации CMake;
если `zlib` не найден в системе (типично для Windows), он тоже скачивается через
`FetchContent`.

### Linux

Debian / Ubuntu:

    sudo apt install build-essential cmake qt6-base-dev qt6-serialport-dev udisks2 eject zlib1g-dev

Fedora: `sudo dnf install gcc-c++ cmake qt6-qtbase-devel qt6-qtserialport-devel udisks2 zlib-devel`
Arch:   `sudo pacman -S base-devel cmake qt6-base qt6-serialport udisks2 zlib`

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
    cmake --build build -j
    ./build/KarabasFlasher --log

### Windows

Установите Qt 6 (комплект MSVC или MinGW) и откройте `CMakeLists.txt` в Qt Creator, либо:

    cmake -S . -B build -DCMAKE_PREFIX_PATH=C:/Qt/6.x.x/<kit>
    cmake --build build --config Release

Для раздачи соберите папку с DLL: `windeployqt build\Release\KarabasFlasher.exe`.
Без подписи кода SmartScreen может показать предупреждение.

### macOS

    brew install cmake qt
    cmake -S . -B build -DCMAKE_PREFIX_PATH="$(brew --prefix qt)" -DCMAKE_BUILD_TYPE=Release
    cmake --build build -j

Упаковка: `macdeployqt build/KarabasFlasher.app -dmg`. Homebrew-Qt собран под одну архитектуру,
поэтому бинарник будет для вашего процессора (arm64 или Intel). Универсальная сборка требует
универсального Qt. Без подписи и нотаризации Gatekeeper блокирует первый запуск: откройте
приложение через «Системные настройки - Конфиденциальность и безопасность - Всё равно открыть».
Начиная с macOS Ventura система может запросить доступ к съёмным томам.

`minizip-ng` и `zlib` собираются через `FetchContent`; отдельно ставить их не нужно.

Ключ `--log` включает запись лога в файл `flasher_log.txt` рядом с исполняемым файлом программы.
Если каталог с программой недоступен для записи (Program Files, `/usr/bin`, `.app` в `/Applications`),
лог сохраняется в пользовательский каталог данных: `~/.local/share/KarabasFlasher/flasher_log.txt` (Linux),
`%APPDATA%\KarabasFlasher\flasher_log.txt` (Windows), `~/Library/Application Support/KarabasFlasher/` (macOS).

## Версии и релизы

Версия задаётся **в одном месте** - `project(KarabasFlasher VERSION X.Y.Z ...)` в `CMakeLists.txt`.
Оттуда она попадает в заголовок окна, в журнал (вместе с описанием из git, например `v0.1.0-3-gabc1234`),
в `--version` и в версию macOS-приложения. Схема `MAJOR.MINOR.PATCH`: исправление ошибки - PATCH,
новая возможность - MINOR, несовместимое изменение - MAJOR. Все три системы проверены на железе,
поэтому используются версии `1.x` (текущая - `1.3.2`).

Как выпустить версию:

    # 1. поднять версию в CMakeLists.txt (project(... VERSION 1.1.0 ...)) и дописать CHANGELOG.md
    git add -A && git commit -m "Release 1.1.0"
    git push
    # 2. поставить тег (строго v + номер из CMakeLists.txt) и отправить его
    git tag v1.1.0
    git push origin v1.1.0

По тегу Actions соберёт три системы и создаст релиз на GitHub с файлами `.dmg`, `.zip`, `.deb` и `.AppImage`.
Если тег не совпадает с версией в `CMakeLists.txt`, выпуск остановится с сообщением об ошибке.
Описание из git считается при конфигурации CMake; при сборке из zip без git будет `no-git`.

## Автоматическая сборка (GitHub Actions)

В `.github/workflows/build.yml` описана сборка под три системы. Положите проект в репозиторий на
GitHub (`git init && git add . && git commit -m init && git push`), откройте вкладку **Actions** -
сборка запустится сама. Готовые файлы лежат в разделе **Artifacts** завершённого запуска:
`KarabasFlasher-macos` (.dmg, universal arm64 + Intel), `KarabasFlasher-windows` (zip с DLL Qt),
`KarabasFlasher-linux-ubuntu24.04` (.deb), `KarabasFlasher-appimage` (AppImage с Qt внутри).
Заодно это проверка компиляции на всех системах. `minizip-ng` и `zlib` собираются через
`FetchContent` прямо в CI, поэтому отдельные пакеты для них не нужны.

Сборки не подписаны. На macOS скачанный из браузера `.dmg` получает карантин: после перетаскивания в
«Программы» выполните `xattr -dr com.apple.quarantine /Applications/KarabasFlasher.app`
или откройте приложение через «Всё равно открыть» в настройках безопасности.

## Настройка системы

### Linux

1. **Доступ к порту.** При ошибке «Доступ запрещён» программа сама предложит установить правило
   udev (`TAG+="uaccess"`) для вашего устройства; пароль администратора запросит polkit (`pkexec`)
   один раз, перелогин не нужен. Если `pkexec` недоступен - добавьте себя в группу `dialout`
   (в Arch и Manjaro - `uucp`) и перелогиньтесь:

       sudo usermod -aG dialout $USER

   При установке из пакета правило `packaging/70-karabas.rules` ставится в `lib/udev/rules.d`
   автоматически (`cmake --install`), и пароль не нужен вообще.

2. **ModemManager** может опрашивать `/dev/ttyACM*` AT-командами и мешать. Найдите VID:PID (`lsusb`)
   и создайте `/etc/udev/rules.d/70-karabas.rules`:

       ATTRS{idVendor}=="XXXX", ATTRS{idProduct}=="YYYY", ENV{ID_MM_DEVICE_IGNORE}="1"

   затем `sudo udevadm control --reload && sudo udevadm trigger`.

3. **udisks2** нужен для монтирования и извлечения SD-карты (`udisksctl` и `gdbus`/`busctl`).
   Извлечение выполняется D-Bus-вызовом udisks `Drive.Eject` (SCSI-eject с правами системы),
   запасной вариант - утилита `eject`. `udisksctl power-off` не используется: он отключает
   питание USB-порта, и Карабас не возвращается в обычный режим.

### Windows и macOS

Дополнительная настройка не нужна: драйвер CDC в Windows 10 и новее встроенный, на macOS порт
виден как `/dev/cu.usbmodem*`.

## Два USB-порта прошивки (26111914)

С 19.11.2026 (сборка 26111914) у платы два CDC-порта:

| Порт | Linux | Назначение |
|---|---|---|
| `control` (interface 0) | `/dev/serial/by-id/usb-Karabas_Go_<serial>-if00` | лог, DIAG, `AT+KARABAS=...`; сброс 1200 бод тоже только здесь |
| `core serial` (interface 2) | `/dev/serial/by-id/usb-Karabas_Go_<serial>-if02` | только UART ядра, без AT-команд и лога |

`MainWindow::updatePortList()` определяет роль порта через `karabasPortRole()`:
на Linux — `bInterfaceNumber` в sysfs (`00`/`02`), запасной вариант — `by-id`-ссылки; на macOS — суффикс
`1`/`3`; на Windows — USB composite interface `MI_00`/`MI_02` из реестра
`HKLM\SYSTEM\CurrentControlSet\Enum\USB` (описание COM-порта локализовано и не подходит).
Control-порт подписывается `[control]` и выбирается
автоматически, core serial — `[core serial]` и для прошивки не используется. Автоопределение модели
запускается, только если выбран control-порт. Прошивка 26111913 также изменила `karabas.ini`: отсутствующие
ключи сохраняют значения по умолчанию.

`MainWindow::pollSerialPorts()` раз в секунду тихо перечитывает список портов, но только пока
control-порт не найден и в списке ничего не выбрано. Как только порт выбран (автоматически или
вручную) либо найден control, таймер останавливается; во время FLASH/MSC опрос также не выполняется
(`m_busy`). Список перестраивается только при изменении набора портов, поэтому ручной выбор
пользователя не сбрасывается, а журнал не засоряется. При появлении control-порта он выбирается,
и один раз запускается `onAutoDetectModel()`; если control-порт исчез, `m_lastAutoDetectedPort`
сбрасывается, чтобы при следующем подключении автоопределение сработало снова.

При `debug=1` прошивка пишет в control-порт много отладочных строк (HID, DIAG и т.п.).
Флешер не выводит весь сырой ответ в окно: на экране только короткий статус команды,
а полный буфер пишется через `logVerbose` в файловый журнал при `--log`.

## Протокол обмена с платой

Программа общается с платой AT-командами по control-порту (115200 8N1):

| Команда | Ответ | Назначение |
|---|---|---|
| `AT+KARABAS=version` | `+KARABAS:<firmware>;<board>;<core id>;<core build>` | версия прошивки и идентификатор платы |
| `AT+KARABAS=list` | по строке `+KARABAS:<file>;<id>;<name>;<build>` на ядро, затем `OK` | ядра на SD-карте и их сборки для текущей платы |
| `AT+KARABAS=boot` | `OK`, затем перезагрузка | переход в BOOTSEL без 1200-бод-сброса |
| `AT+KARABAS=msc` | `OK` | режим кард-ридера, карта №1 (основная, с ядрами) |
| `AT+KARABAS=msc2` | `OK` | режим кард-ридера, карта №2 (дополнительная) |
| `AT+KARABAS=state` | `+KARABAS:core;...`, `+KARABAS:osd;...`, строки `item`, затем `OK` | текущее ядро, OSD и файловые пункты |
| `AT+KARABAS=load:<file или id>` | `OK` | запустить ядро |
| `AT+KARABAS=reset` | `OK` | перезапустить текущее ядро |
| `AT+KARABAS=osd` / `osd:<item>` / `osd:<item>=<value>` | строки `+KARABAS:item`, затем `OK` | прочитать или изменить пункты меню ядра |
| `AT+KARABAS=mount:<item>:<path>` / `eject:<item>` | `OK` | подключить или отключить образ диска |
| `AT+KARABAS=key:<keys>` / `type:<text>` / `hold:<key>` / `release` | `OK` | эмуляция клавиатуры |
| `AT+KARABAS=mouse:...` / `click:...` / `pad:...` / `padhold:...` | `OK` | эмуляция мыши и джойстиков |
| `AT+KARABAS=sync` | `OK` после доставки очереди ввода | дождаться `key` / `type` / `mouse` / `click` / `pad` |
| `AT+KARABAS=debug:0` / `debug:1` | `OK` | отладочный лог до перезагрузки |
| `AT+KARABAS=sd2test` | строки диагностики, затем `OK` | проверка второй SD-карты (только boot core) |
| `AT+KARABAS=esp` / `uart` | `OK` | мост на ESP8266 и обратно на UART ядра |

Идентификатор платы в ответе на `version`: `1` — Karabas Go, `2` — Karabas Go Mini rev A-F,
`3` — Karabas Go Mini rev G. Ответ `ERROR` означает, что прошивка не поддерживает команду.
Текущая прошивка (сборка 26111418) поддерживает весь список; флешер использует `version`, `list`,
`msc` и `msc2`. `Worker::runDetectModel()` отправляет `version`, затем сразу `list` — и при
автоопределении модели на старте, и по кнопке с лупой. Ответ `list` разбирает
`parseCoreListResponse()`: список используется для сравнения версий, а подробный вывод идёт
только в файловый verbose-журнал (`--log`), не на экран. `boot` — основа следующего шага,
более надёжного перехода в BOOTSEL.

## Проверка обновления флешера

`Worker::checkFlasherUpdate()` запрашивает
`https://api.github.com/repos/xdemax/kgff/releases/latest` с таймаутом 5 с. `tag_name`
сравнивается с `APP_VERSION` через `versionIsNewer()`, причём префикс `v` и компоненты
`MAJOR.MINOR.PATCH` учитываются. Если релиз новее, испускается
`appUpdateAvailable(tag, html_url)`. `MainWindow::onAppUpdateAvailable()` показывает красную
кликабельную надпись `New flasher version available` в главном окне над кнопкой
`Download via GitHub`; `QLabel` с `openExternalLinks` открывает страницу релиза в браузере.
Панель ядер при этом не раскрывается.
Проверка выполняется после успешной стартовой проверки версий прошивки; ошибки только пишутся
в verbose-журнал и не мешают работе.

## Версия прошивки на GitHub

В дереве `firmware` версия не входит в имя файла: она записана в сообщении последнего коммита
каждого файла, например `Firmware build 26111813: ...`. `Worker::fetchLatestFirmwareVersion()`
берёт Atom-ленту истории выбранного файла:

    https://github.com/andykarpov/karabas-go/commits/master/firmware/<file>.atom

и разбирает заголовок регуляркой `Firmware build\s+([0-9]+)`. Если лента недоступна или формат
не распознан, используется запасной GitHub API
`/repos/andykarpov/karabas-go/commits?path=firmware/<file>&per_page=20`. Запрос выполняется в
`doDownload()` при `updateFirmware || updateCores`; результат пишется в журнал как
`Latest firmware on GitHub (<file>): <build>`, а ошибка запроса не блокирует скачивание.

На старте порядок такой: `MainWindow::startStartupFlow()` сначала проверяет, выбран ли control-порт.
Если выбран — запускается `onAutoDetectModel()` (`AT+KARABAS=version` и `AT+KARABAS=list`), и только
после завершения этой операции (успешной или нет) запускается
`Worker::runStartupFirmwareCheck()`. Проверка идёт параллельно по трём файлам: до трёх раундов
Atom-запросов с таймаутом 5 с, повторяя только неудачные модели. После неё испускается
`startupFirmwareCheckFinished`; `maybeAutoDetectPort()` вызывается только для случая, когда плату
подключили позже и порт появился во время проверки. Если порта при старте нет, проверка прошивок
запускается сразу, а автоопределение — при появлении control-порта.
В экранный журнал выводится
одна строка — `Firmware versions fetched.` или `Warning: Firmware version fetch error.`;
подробности по моделям идут в файловый verbose-журнал. Если проверка не удалась, приложение
продолжает работу. После проверки `emitFirmwareStatus()` обновляет статус прошивки в панели ядер
с учётом уже известной версии платы.

`AT+KARABAS=version` даёт установленную сборку прошивки (`m_boardFirmwareVersion`). Если при
скачивании ядер известны обе версии, `doDownload()` сравнивает их через `compareCoreBuilds()` и
испускает `firmwareStatusReady(known, needsUpdate, installed, latest)`. Панель
`CoreVersionsPanel::setFirmwareStatus()` показывает справа вверху:
- старую прошивку — красным мигающим `Firmware needs an update!` (мигание — `QTimer`, 600 мс);
- актуальную — зелёным `Firmware is up to date.`;
- неизвестную — ничего.
Статус показывается только когда обновляются ядра (`updateCores`). После успешной прошивки
`doFlash()` ждёт появления порта, снова вызывает `queryVersion()` и обновляет статус. Если новую
версию подтвердить не удалось, сохранённая версия очищается и статус скрывается, чтобы не
показывать устаревшее значение.

## Версия ядра в `.kg`

Скачанные ядра разбираются в `src/CoreFile.cpp` (`parseCoreFile()`), а заголовки, прочитанные
по HTTP Range, — через `parseCoreHeaderData()`. Оба используют общий `parseCoreImpl()`. Формат kgo2 описан в
[`karabas-go-tools/docs/kgo2.md`](https://github.com/andykarpov/karabas-go-tools/blob/master/docs/kgo2.md)
и в `lib/common/kg2_format.h` прошивки. Для чтения версии нужны только заголовок и две секции:

- заголовок 32 байта: сигнатура `kgo2` (0), версия (4), размер заголовка (6), число секций (8),
  размер записи таблицы (10), маска плат (12), все числа little-endian;
- таблица секций начинается с `header_size`; запись 16 байт: тип (0), маска плат (2),
  смещение (4), длина (8);
- `STRINGS` (тип 1) — пул строк с NUL-терминаторами; `CORE` (тип 2) — запись ядра: размер (0),
  ссылки на строки `id` (2), `name` (4), `build` (6); `BITSTREAM` (9) или `BITSTREAM_LINK2` (10)
  — битстрим платы;
- в одном `.kg` может быть несколько секций `CORE` — по одной на плату. Версия читается из
  секции той платы, которая выбрана в интерфейсе; `AT+KARABAS=list` возвращает `build` именно
  для платы, на которой запущена прошивка;
- если для выбранной платы в файле нет `CORE`/битстрима (например, `pong.kg` только для Karabas
  Go), парсер возвращает `NotForBoard`, а не ошибку.

`build` — строка вида `26111345`: первые две цифры — год, затем месяц, день и номер сборки.
Такие версии можно сравнивать как строки: длина и формат у ядер одинаковы.
Парсер проверен на всех 46 ядрах текущего набора `karabas-go`.

## Скачивание ядер по выбору

Полный набор ядер — около 100 МБ, поэтому `Download via GitHub` больше не качает его целиком:

1. `MainWindow::onDownload()` ставит `Params.prepareCores=true`.
2. `Worker::prepareCores()` получает список файлов через GitHub API и читает первые 64 КБ
   каждого `.kg` HTTP Range-запросом (`fetchRanges()`, 8 параллельно). Это около 3 МБ на весь
   набор; версии и поддержка платы определяются через `parseCoreHeaderData()`.
3. Список сравнивается с `AT+KARABAS=list` и показывается в панели с колонкой `Available`.
   Старый маркер `cores/download_complete.txt` удаляется как признак устаревшего набора;
   для выбранных ядер маркер не нужен — FLASH проверяет и докачивает их сам.
4. Пользователь отмечает нужные ядра и нажимает **FLASH!**. Отдельной кнопки скачивания нет:
   `doFlash()` вызывает `ensureSelectedCoresDownloaded()` и докачивает только те выбранные
   файлы, которых ещё нет в `cores/`. Уже скачанные файлы повторно не загружаются.
5. Скачивание выполняется до переключения платы в MSC и до любых изменений на SD-карте. Если
   хотя бы один выбранный файл скачать не удалось, FLASH завершается ошибкой, карта не трогается.
   При подготовке списка `download_complete.txt` не требуется: наличие выбранных файлов
   проверяется напрямую.
6. `MainWindow::onFlash()` сразу сворачивает правую панель. После завершения FLASH с обновлением
   ядер панель очищается (`m_coreListPrepared=false`, старый маркер удаляется), чтобы не
   показывать устаревшие `Installed`. Для обновления прошивки без ядер панель не очищается.

При подготовке списка `knownCoreFiles` (все имена с GitHub) передаётся в `doFlash()`, поэтому
ignored-ядро переносится в backup даже если его полный файл не скачивался. Пользовательские
`.kg`, которых нет в релизном списке, по-прежнему не трогаются.

## BACKUP: откат прошивки и ядер

`MainWindow::onFlash()` проверяет `QGuiApplication::keyboardModifiers()`: с зажатым Shift
кнопка называется `BACKUP` и запускает не обычную прошивку, а подготовку отката.
`Worker::doPrepareRollback()` ничего не пишет:

1. `queryVersion()` даёт установленный build и board id; по board id выбирается файл модели.
2. `fetchFirmwareRevisions()` читает историю `firmware/<файл>` (GitHub API, при ошибке — Atom),
   находит установленный build и берёт следующий, более старый коммит.
3. `findLatestBackupOnSd()` входит в MSC, монтирует карту, ищет самый новый непустой
   `backup_*` с `.kg`, запоминает имя и количество файлов и извлекает карту.
4. `rollbackPrepared(RollbackInfo)` передаёт данные в GUI. `MainWindow::showRollbackDialog()`
   показывает два независимых чекбокса — прошивка и ядра; недоступные пункты disabled.

После подтверждения `Worker::doRollback()`:

- сначала скачивает и проверяет `.uf2` (если выбрана прошивка), чтобы при сетевой ошибке
  не трогать карту;
- при выборе ядер вызывает `restoreCoresFromBackup()`: копирует все `.kg` из выбранного
  `backup_*` в корень с заменой, без создания нового backup и без удаления остальных файлов;
- если выбрана прошивка, передаёт скачанный файл в обычный `doFlash()`.

Ограничения: `.kg1/.kg2/.kg3` не восстанавливаются; ignored-ядра из backup возвращаются;
safety-backup текущих ядер не создаётся; при повторном BACKUP будет выбран уже следующий
по времени `backup_*`, если он появился.

## Сравнение версий ядер

`Worker::prepareCores()` и старый путь полного скачивания сравнивают разобранные заголовки с
последним успешным `AT+KARABAS=list` (`m_deviceCores`). Если списка для выбранной платы ещё нет,
а порт выбран, `queryCoreList()` запрашивается перед показом окна.

- Ядро ищется по имени файла без учёта регистра, запасной ключ — `id` ядра.
- `compareCoreBuilds()` сравнивает версии как числа (обычно 8 цифр), иначе как строки.
- равные версии — обычный цвет;
- доступная версия новее установленной — вся строка зелёная;
- ядра нет на карте — зелёная строка `not installed > доступная версия`, отмечена по умолчанию;
- установленная версия новее доступной — вся строка жёлтая;
- ядро не для этой платы — красная строка `file > not supported for your Karabas`;
- заголовок не читается — красная строка с причиной;
- если список с карты недоступен, установленная версия показывается как `unknown` и выводится
  подсказка подключить плату и нажать лупу.

Правая панель главного окна — `CoreVersionsPanel`: таблица `QTableWidget` с колонками выбора,
`Core`, `Installed`, `>`, `Available` (для списка с GitHub) и заголовком
`Available cores for <модель>`; после старого полного скачивания используется заголовок
`Downloaded cores for <модель>` и колонка `Downloaded`. Панель
скрыта по умолчанию; кнопка `>>`/`<<` вызывает `MainWindow::showCorePanel()` /
`hideCorePanel()`. При раскрытии окно расширяется примерно вдвое и центрируется по итоговой
ширине обеих половин (`centerWindowForWidth()`), чтобы правая панель не уезжала за экран;
при нехватке места ширина ограничивается экраном. После подготовки списка
`onCoreVersionsReady()` заполняет панель и раскрывает её автоматически.
По умолчанию отмечены только зелёные строки (доступная версия новее установленной); остальные
можно отметить вручную. Точка выбора имеет три состояния: `Checked` — обновить, `Unchecked` —
пропустить, `PartiallyChecked` — **ignored** (не трогать никогда). Игнорируемая строка делается
тёмно-серой, в `Installed` пишется `ignored`; список хранится в `QSettings` (`ignoredCores`) и
переживает перезапуск. Точки рисует делегат `CheckDotDelegate`: зелёная — обновить, тёмно-серая —
ignored, серая/красная — не выбрано (`not supported` — красная). Строку с ошибкой заголовка
отметить нельзя.

Чекбокс `All selected` имеет состояния все, ни одного и только новые; произвольный набор
показывается как `custom`. Игнорируемые строки в счётчике `Checked: N of M` и в `All selected`
не участвуют. Список `selectedCoreFiles` из `Params` передаётся в `doFlash()`, а постоянный
список `ignoredCoreFiles` пересекается с `knownCoreFiles` (всеми именами с GitHub), поэтому
ignored-ядро переносится в `backup_*`, даже если его полный файл не скачивался. Полные файлы
для копирования — только те, что пользователь отметил; FLASH докачивает их перед записью.
`updateCoresOnSd()` копирует выбранные ядра, а старые файлы ignored переносит в `backup_*`,
чтобы убрать их с карты. Пользовательские `.kg`, которых нет в наборе
GitHub, не переносятся; старые `.kg1/.kg2/.kg3` бэкапятся только если их основа совпадает с
релизным ядром (`alf.kg1` для `alf.kg`).

## Как программа находит диск

Диск не ищется по букве, пути или метке. Перед командой MSC делается снимок съёмных дисков с
готовым носителем, а SD - это диск, у которого носитель появился после команды. Загрузчик
RP2040 ищется по метке `RPI-RP2`. Если подходящих дисков несколько, программа останавливается
с сообщением, а не угадывает.

На Windows `RPI-RP2` ищется среди **всех** логических дисков, а не только `DRIVE_REMOVABLE`:
RP2040 в режиме загрузчика иногда определяется как `DRIVE_FIXED`, и фильтр по типу терял диск.
Метка тома читается с несколькими повторными попытками: сразу после появления буквы Windows
может ещё не дочитать её.

## Проверка диска перед записью

Перед записью на SD-карту вызывается `Worker::confirmDrive()`:

- на диске есть ядра `.kg` (или старые `.kg1`/`.kg2`/`.kg3`) или папка `backup_*` — запись начинается без вопросов;
- диск пустой — запись начинается с предупреждением в журнале;
- файлы есть, но признаков Карабаса нет — рабочий поток шлёт сигнал `confirmUnrecognizedDrive`
  через `Qt::BlockingQueuedConnection`, GUI показывает диалог с узлом, меткой, размером и списком
  файлов, ответ возвращается обратно. При отказе диск не извлекается (он чужой), а `abortReason`
  равен `unrecognized drive`.

## Защита от чужой платы в BOOTSEL

Если порт Карабаса ещё жив, а `Platform::bootloaderDisks()` уже не пуст, значит диск `RPI-RP2`
принадлежит другой RP2040-плате (у живого Карабаса в нормальном режиме его быть не может).
Проверка `Worker::foreignBootloaderPresent()` выполняется в обеих ветках прошивки (с MSC-сеансом
и без него) и прерывает операцию с сообщением «Another RP2040 board is in BOOTSEL mode».

## Дополнительный контент (`extra.zip`)

**Сейчас пункт `Download extra content` временно отключён в интерфейсе до доработки архива.**
Код скачивания/распаковки оставлен для следующего шага.

Архив `extra.zip` скачивается с GitHub и распаковывается встроенной библиотекой `minizip-ng`
(собирается через `FetchContent`). Внешние архиваторы не используются. При распаковке:

- проверяется CRC каждого файла (`mz_zip_reader_entry_close`) и целостность каталога
  (`MZ_END_OF_LIST`);
- считается фактически записанный объём (лимит 2 ГБ), а не только заявленный в каталоге;
- проверяется свободное место в кэше перед распаковкой;
- имена с компонентом `..`, абсолютные пути и обратные слеши отсекаются;
- симлинки из архива не копируются на SD-карту.

Содержимое верхней папки `extra/` (если она есть в архиве) копируется в корень SD-карты без
вложенной папки. Остальные элементы корня копируются как есть. Файлы, которых нет в архиве,
на карте не трогаются.

## Диагностика

Все три платформы проверены на железе: скачивание прошивки и ядер, прошивка RP2040, обновление
ядер на SD-карте, режим кард-ридера. При проблемах запустите программу с `--log` и пришлите файл лога.
